# Streaming replay on macOS

The release probe feeds deterministic native Float32 buffers into `PreparedCaptureTap.accept`. A synthetic input driver supplies the format and source clocks. The production PCM handoff, serial actor, lifecycle pump, scheduler, result publisher and three independent subscriptions perform the work. Running the probe requires macOS 27 and Swift 6.4. It opens no audio device and requests no permission.

## Reproduce

```sh
python3 Tools/Streaming/build.py .build/streaming
binary=.build/streaming/swiftpm/release/StreamingReplayProbe
"$binary" core 48000 mixed paced disabled 2 7 single /tmp/core-replay.json
python3 Tools/Streaming/benchmark.py .build/streaming/build.json full .build/full-streaming-results
python3 Tools/Streaming/trace.py .build/streaming/build.json .build/streaming-signposts.json
```

For trace acquisition the controller launches the replay, attaches Instruments to that process and waits for the recorder to signal readiness. The target writes the completed trial atomically. The controller checks its workload and numerical hash, stops the recorder, then releases the target after Instruments exits. This wait occurs after measurement. Each invocation leaves a sibling `*-attempts-*.json` journal with phase transitions, attempt numbers and outcomes. A startup, finalization or export timeout, or incomplete signpost accounting, allows up to three recordings per workload. A numerical or metadata mismatch fails the run. The signpost result is published only after all three workloads pass validation.

The builder requires a fresh directory and binds the release executable to the source digest, Git revision and compiler. Every group verifies this receipt before and after measurement. Use a fresh output directory for each benchmark group. The default runner checks the toolchain pinned in `Configuration/build.json`. Use `--development-toolchain` for a separately labelled local run. Groups `cpps`, `core` and `full` cover 44.1/48 kHz and 64, 128, 256, 512, 1024 and mixed callbacks, each at native pace and at maximum sustainable throughput. The mixed pattern also includes 93 and 711 frames. The one-second deterministic source repeats seeded voiced harmonics, silence and a clipped segment. Each run includes a 20 ms jump in the device sample clock.

| Group | Question |
| --- | --- |
| `overhead` | How do the same input and outputs compare across disabled, sampled and detailed instrumentation? Six repetitions per profile rotate the mode order and preserve paired wall-time deltas with each mode’s production timer behavior. |
| `stress` | Does overflow recover? A 32-slot queue receives 36 callbacks before worker preparation, followed by backpressured input. The group also reconfigures and restarts one lifecycle, cancels during a publication with a queue backlog, and overlaps two analyzers on separate streams. |
| `capacity` | How does buffer capacity affect the same full-profile paced input? Compare 32 and 512 slots at both rates and two callback geometries. |
| `soak` | How do retained capacity, queue occupancy and resident memory behave over 120 seconds? One run uses backpressure and one uses paced input. Both use the full profile, mixed callbacks and constant-size metric status counters. |
| `trace.py` | Which stages executed, how long did they take, and did valid CPPS reach the consumer after an overrun? The Logging template captures a paced CPPS run, a controlled burst and a full-profile throughput run. |

CPPS uses a finite-FIR preview, 10 ms hops, centered smoothing and a least-squares prominence fit. Core adds unweighted and K-weighted levels plus raw and tracked YIN. Full adds causal HNR and SWIPE′. The runner retains the entire composition hash and each lane’s support, filter warmup, smoothing lookahead, hop and worker tiling allowance. Whole-file suite measurements are documented separately. [Voice algorithm benchmarks](voice-algorithm-benchmarks.md)

## Read the measurements

The paced producer schedules each arrival at the acoustic end of its callback on an independent monotonic timeline. The maximum-throughput producer waits outside the tap for queue space. Only paced runs report acoustic result age. Throughput divides **accepted source duration** by elapsed time from the first callback entry until the lifecycle has drained and published the last admitted block. Aggregate worker processing time sums individual nonempty worker turns.

- Callback durations cover one native tap call. Signal generation, SDK buffer preparation, snapshot sampling and clocks around the call belong to the harness.
- Queue residence has a measured interval. The enqueue occurs inside the tap, so dequeue minus callback return is a lower bound, clamped at zero when publication races callback return. Dequeue minus callback entry is an upper bound. The join verifies matching block host anchors, sample counts and order.
- Per-frame timing uses the native metric observation window’s exclusive acoustic end, publication time, and actual `next()` observation time. Per-lane intrinsic delay, filter/smoothing lookahead and the 256-frame tile allowance are reported separately. The operational deadline counts observations later than dependency-support end plus one native hop. Individual callback misses compare tap duration with its own chunk duration. These are fixture-specific observations.
- Each short run retains all callback and drain records and one record per delivered frame. Percentiles use the nearest rank of individual observations. Trace spans measure resampling, pre-emphasis, assembly, FFT, cepstrum, CPP, smoothing, fitting, and publication. Delivery marker counts and their recorded mailbox lag establish observation. Some stages nest. Adding inclusive spans would double-count work. An independent native scheduler counts every completed DSP interval by stage and profile. The runner reconciles those counts with the trace and verifies process identity, numeric metadata, publication and delivery markers, acquisition gaps and post-gap recovery. Raw system traces stay local.
- Every admitted contiguous region goes through an independent memory schedule in 173-frame partitions. Comparison covers the complete native frame, scientific timing, coverage, validity and numeric values. Cross-mode SHA-256 checks normalize run-specific stream identifiers and absolute clocks. Missing input is counted in source frames. A second schedule with every offered callback counts exact observation-window positions lost or introduced by the new grid after capacity drops. Flushing the direct final region counts frames withheld by explicit stop without publishing them as live values.
- The fast strict consumer has 256 slots. The delayed newest-value consumer has two slots and waits 40 ms between observations. A paused strict consumer has four slots and must report overflow after draining its four accepted values. Gap, reset, reconfiguration, completion and cancellation checks require cleared old results.
- For the soak, the observer retains at most about a dozen RSS checkpoints and per-metric outcome totals. It discards callback and frame histories. PCM bytes count preallocated audio slots. Scheduler bytes count the worker’s reported numerical scratch. The subscriber and in-flight result batch capacities additionally bound retained result *counts*. Sampled resident bytes include SDK buffers, the Swift runtime, allocator retention and the harness itself.

## Evidence and integration

The CI workflow retains per-group `results.json` and checksummed compressed unbatched receipts. Each result identifies the commit, executable digest, compiler, SDKs, host model and build, preflight power observations, arguments, seed, capacities, and availability denominators. The trace group registers for the Instruments recording-start notification before launching the probe. A private readiness file releases the target, and one-second guard intervals bracket replay outside its measured clocks. The trace group retains a numeric stage summary and export digests. After downloading the seven timing and lifecycle artifact directories, run `python3 Tools/Streaming/catalog.py catalog.json streaming-replay-*/results.json`. The exporter recomputes every summary from the checksummed native records, checks the requested workload and capacity, and requires all groups to share a clean measured Git revision. The dashboard can compare matching profile, workload, host and build identities. [Dashboard issue](https://github.com/plx/hdxl-voice-processing/issues/62)

Two companion PR checks provide separate capture-side evidence. The capture-adapter job measures 40 real tap workloads with positive allocator and ARC controls and requires zero measured heap activity across the tap histograms. The transport audit inspects optimized tap and handoff assembly in four Apple target slices, checks the bounded admission path and rejects unrecognized calls. SDK format/time getters and scoped buffer borrowing remain identified framework boundaries. Actual device delivery, callback scheduling, energy and thermal measurements have their own follow-up. [Capture benchmark](../../Tools/Capture/benchmark.py) · [Transport audit](../../Tools/Transport/audit_callback.py) · [Physical measurement protocol](https://github.com/plx/hdxl-voice-processing/issues/74#issuecomment-7128253069)

The first local 48 kHz, 512-frame run on an Apple M1 Max (Mac13,1, macOS 27.0.1, Xcode 27.2) admitted all 96,000 offered frames for each profile. CPPS-only, core and full unpaced throughput factors were 55.25×, 22.24× and 1.93×. Their paced CPPS source-end-to-observation p99s were 32.0, 34.0 and 313.9 ms. Smaller chunks on the full profile could fill the queue during sustained expensive turns. At 64 frames it dropped 9,920 source frames at 48 kHz. These initial development measurements identify a tail-latency case for optimization. The issue retains the commands and the comparison protocol. [Optimization case](https://github.com/plx/hdxl-voice-processing/issues/65#issuecomment-7128432719)

A subsequent full-profile recording attributed the tail to HNR period search. Its 61 intervals had a 0.157 ms median and a 49.46 ms maximum. HNR correlation peaked at 0.069 ms. All 31 native stage/profile counts matched the independently instrumented memory replay. [Stage attribution](https://github.com/plx/hdxl-voice-processing/issues/65#issuecomment-7128846670)
